# MolfMaps Constitution

## Core Principles

### I. Simplicity First (YAGNI)

The project is a small interactive-maps website; solutions MUST favor the
simplest approach that satisfies the current requirement. Contributors MUST NOT
add abstractions, layers, services, or dependencies for anticipated-but-absent
needs. Any added complexity (new library, new architectural layer, new service)
MUST be justified in writing against a simpler rejected alternative.

**Rationale**: Small projects die from premature complexity. Keeping the surface
area minimal keeps the codebase understandable and maintainable by a small team.

### II. Clear API Contracts

The backend MUST expose functionality through explicit, typed FastAPI endpoints.
Every request and response body MUST be modeled with Pydantic models (no raw,
untyped dicts crossing the API boundary). The OpenAPI schema generated by FastAPI
is the single source of truth for the frontend/backend contract and MUST remain
accurate.

**Rationale**: A typed, self-documenting contract lets the JavaScript frontend
and Python backend evolve independently without guesswork or drift.

### III. Frontend/Backend Separation

The JavaScript frontend and the Python FastAPI backend MUST remain cleanly
separated: the frontend communicates with the backend ONLY over HTTP (the REST
API). Business logic MUST live in the backend; the frontend is responsible for
presentation, map rendering, and user interaction. Backend code MUST NOT depend
on frontend build artifacts to function.

**Rationale**: A clear boundary keeps concerns isolated, enables independent
testing, and allows either side to be swapped or upgraded with minimal blast
radius.

### IV. Reproducible Environments

All Python development and execution MUST occur inside a virtual environment
(`venv`). Dependencies MUST be declared with pinned versions in a tracked
manifest (e.g. `requirements.txt`), and the environment MUST be reconstructable
from that manifest alone. Frontend dependencies MUST likewise be declared in a
tracked manifest. Contributors MUST NOT rely on globally installed packages.

**Rationale**: Reproducible environments eliminate "works on my machine" failures
and make onboarding and deployment deterministic.

### V. Pragmatic Testing

Critical backend paths — API endpoints and the logic behind map data handling —
MUST have automated tests before a feature is considered complete. Tests are
required for behavior that would break silently or is hard to verify manually;
exhaustive coverage of trivial code is NOT required. A change MUST NOT be merged
if it breaks existing tests.

**Rationale**: Testing the risky parts protects the project without imposing the
ceremony overhead that would slow a small team.

## Technology & Architecture Constraints

- **Backend**: Python with the FastAPI framework, served by an ASGI server
  (e.g. Uvicorn). Backend logic MUST run inside a Python `venv`.
- **Frontend**: JavaScript, delivering the interactive map UI in the browser.
- **Interface**: The frontend and backend communicate exclusively over an HTTP
  REST API defined by FastAPI.
- **Domain**: The application centers on interactive maps; map-related data and
  interactions are the primary domain concern.
- New runtime dependencies or additional services beyond this stack MUST be
  justified under Principle I before adoption.

## Development Workflow

- Activate the Python `venv` before running, testing, or installing backend
  dependencies.
- Add or update dependencies through the tracked manifests with pinned versions;
  never commit code that depends on unpinned or globally installed packages.
- Every change SHOULD keep the FastAPI OpenAPI schema consistent with the
  frontend's expectations.
- Run the test suite locally before merging; merges that break existing tests are
  not permitted.
- Reviews MUST verify compliance with the Core Principles, flagging unjustified
  complexity in particular.

## Governance

This constitution supersedes other ad-hoc practices for the MolfMaps project.
Amendments MUST be documented via an update to this file, accompanied by a version
bump and a Sync Impact Report describing the change and its effect on dependent
templates.

Versioning follows semantic versioning:
- **MAJOR**: Backward-incompatible governance changes or removal/redefinition of a
  principle.
- **MINOR**: Addition of a new principle or materially expanded guidance.
- **PATCH**: Clarifications, wording, or non-semantic refinements.

All pull requests and reviews MUST verify compliance with these principles. Any
deviation MUST be justified in writing, and unjustified complexity MUST be removed
before merge.
